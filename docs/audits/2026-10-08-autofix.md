# Audit et corrections — 8 octobre 2026

Cette passe porte sur le code livré après le [chantier précédent](2026-10-07-implementation.md) : bibliothèque, imports, modifications concurrentes et maintenance du pack. Les suites générales couvrent aussi notation, final, audio, accès, récupération et persistance. Aucun contournement de rôle supplémentaire n’a été démontré. Il s’agit d’un audit local ciblé, pas d’un pentest exhaustif ni d’une nouvelle analyse de la vidéo.

## Défauts traités

| Référence | Défaut et conséquence | Correction et preuve |
|---|---|---|
| R01 | Un ZIP avec des en-têtes valides et un flux Deflate invalide déclenche une exception non interceptée et une erreur serveur. | Refus HTTP 400, métadonnées intactes et libération du créneau d’import. Régression HTTP reproduite en échec avant correction, puis réussie. L’accès reste réservé à l’hôte. |
| R02 | Activation et changements groupés n’envoyaient pas la révision attendue : les tags d’un autre écran pouvaient être remplacés silencieusement. | Révision envoyée pour chaque changement et avancée après chaque sauvegarde du lot. Arrêt au premier conflit, progression partielle et explication conservées. Quatre parcours FR/EN sur Chromium/WebKit simulent une édition concurrente entre deux requêtes. |
| R03 | La génération Docker et la copie vers un nouveau pack n’appliquaient pas de droits Windows explicites : les secrets pouvaient hériter de lecteurs supplémentaires du dossier parent. | Dossier privé avant écriture, fichiers privés après copie, réparation des configurations existantes et refus des liens/jonctions. Tests avec un parent lisible par Everyone. Droits appliqués par .NET sans changer le propriétaire du dossier. Si un ancien fichier permet la lecture/remplacement mais refuse le changement de droits, une copie privée identique le remplace atomiquement. Le cas est testé sous Windows et a été rencontré sur la configuration réelle. |
| R04 | La sauvegarde copiait des fichiers pendant leur modification et pouvait mélanger deux instants de l’état. | Arrêt propre des services, copie stable, redémarrage des seuls services précédemment actifs, y compris après échec de copie. Tests avec Docker simulé, sans accéder au daemon. |
| R05 | Une restauration fusionnait les dossiers et pouvait laisser des fichiers ultérieurs ; l’identité/configuration du Bridge n’était pas sauvegardée. | Sauvegarde format 2 avec état, Bridge, volumes et images. Vérification des fichiers indispensables avant arrêt, remplacement complet du dossier et restauration atomique du fichier Bridge. Échecs de copie et d’installation testés : l’état original reste présent. Les anciens backups incomplets nécessitent une restauration manuelle vérifiée. |
| R06 | Un échec de démarrage ou de restauration pouvait laisser une installation partiellement changée, sans reprise automatique. | Sauvegarde de sécurité avant mutation ; tentative de récupération des données, du Bridge, de la configuration et des images précédentes. En cas d’échec de récupération, message explicite avec la sauvegarde à conserver. Succès et échecs simulés sous Windows PowerShell 5.1. |
| R07 | La bibliothèque pouvait rouvrir avec un résultat ancien chargé pendant sa fermeture. | Rafraîchissement à l’ouverture. Les tests attendent la fin effective du chargement avant de simuler l’édition concurrente ; ils ne dépendent pas de la vitesse du navigateur. |

Les sauvegardes de maintenance excluent caches audio, fichiers musicaux et autorité Caddy. Les guides FR/EN expliquent la courte interruption, la sauvegarde avant **Arrêter**, la confirmation de restauration et le diagnostic d’un échec. Les chemins de maintenance contenant une virgule sont refusés avant restauration, car le montage CLI Docker les interprète comme des séparateurs.

- **1 157 tests Python réussis** : 1 112 dans la suite générale, 44 FFmpeg avec le PATH du processus corrigé, puis une nouvelle régression sur les droits d’un ancien fichier. Deux exclusions Windows : permissions POSIX et création de lien indisponible. Onze intégrations séparées sont couvertes par la CI.
- **52 tests Web réussis** ; build et TypeScript réussis. Ruff, formatage, Pyright, Biome et schéma de protocole réussis.

Les premières exécutions ont trouvé une course dans la préparation du test ; le contrôle de fin de chargement la supprime. - **14 régressions de maintenance/restauration réussies** : neuf cas Windows, cinq cas de remplacement exact, de panne et de restauration du Bridge. Les neuf tests Windows n’utilisent pas le daemon Docker. Ils figurent désormais aussi dans le job Windows de la CI ; leurs résultats sont inclus dans les totaux précédents.
- Protocole **10** et snapshot **8** conservés. Pas de migration de données dans cette passe.

## Scan de sécurité et livraison

Les scans se font localement avec Grype épinglé, réseau désactivé, images exportées par identité immuable et sans montage des volumes ou du socket Docker. Seule la base d’avis est téléchargée ; aucun inventaire n’est transmis à Docker Scout ou à un autre service cloud.

La base a été téléchargée le 8 octobre ; la dernière version disponible est **v6.1.10, construite le 7 octobre à 06:31:48 UTC**. Résultats :

| Image / composant | Critiques | Élevées | Moyennes | Faibles |
|---|---:|---:|---:|---:|
| Application | 0 | 55 | 50 | 10 |
| Bridge | 0 | 55 | 50 | 10 |
| Caddy | 0 | 8 | 14 | 8 |
| FFmpeg 9.0.2 compilé, source vérifiée | 0 | 0 | 0 | 0 |
| 132 composants npm du lockfile, dont 32 de production | 0 | 0 | 0 | 0 |

Les alertes élevées ne proposent pas de correctif dans cette base : 51 `wont-fix` et quatre `not-fixed` par image Python, huit `unknown` pour Caddy. Elles ne sont pas déclarées faux positifs et ne prouvent pas, à elles seules, une exploitation distante. Deux alertes Python moyennes annoncent des versions 3.15/3.15 alpha ; le projet valide actuellement Python 3.12–3.14 et borne `<3.15`. Une migration avec validation dédiée reste nécessaire avant de traiter ces correctifs. L’absence de correspondance pour FFmpeg/npm concerne cette base et ces composants déclarés, pas l’absence de toute vulnérabilité.

Images vérifiées : application `sha256:1bd659e7a076d17964ace9a1e64dcc00bc662d98152903db7e2a10340bc530bd`, Bridge `sha256:335ddad9e59a689ecbcc4709f2e624d4e17c364753cbcfe9e5a48b247ce509f2`, Caddy `sha256:b2877ff4fb23df45e83eb48e5dad0756b72b74468222f4cea6a1afc412506193`.

La sauvegarde native format 2 a été effectuée et toutes ses empreintes vérifiées. L’application corrigée est déployée sur le LAN ; application et Caddy sont sains, Bridge en ligne. La comparaison après relance conserve **deux joueurs, 12 archives et 68 morceaux**, les identités, réponses, scores, métadonnées, cookies, code partagé, configurations et montages. Aucun morceau n’a disparu du catalogue et aucun fichier musical n’a été modifié. Le certificat est inchangé et la connexion HTTPS vérifiée avec l’autorité locale. Les premiers essais de réparation des droits ont été refusés par Windows ; le lanceur corrigé démarre ensuite normalement et les octets de configuration sont conservés.

Preuves privées : `.local/audit-20261008-image-scan/`, `.local/audit-20261008-python.log`, `.local/audit-20261008-ffmpeg.log`, les résultats navigateur et `.local/audit-20261008-runtime-facts.json`. Les données de session et backups restent privés. Le pack est un candidat local non signé ; ce rapport ne valide pas une release publique sans réserve. Les interruptions audio sur téléphones physiques, l’installation sur machine vierge et le cycle complet de restauration de volumes dans une installation indépendante restent à vérifier manuellement.
