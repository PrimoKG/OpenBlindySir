# V0.5 — private Bridges, history and recovery

**0.5.0.dev0**, in development. Implemented in source; no release or artifact
publication is announced. V0.2 already provided multiple sources and owner/track
references; V0.3 added distribution and MC selection. V0.5 adds separate
credentials, managed history, accessibility and recovery checks. [Français](v0.5.md).

## Bridge identity and credentials

Each device keeps its UUID in `config.toml`, a readable name of 1–24 characters
and a distinct secret. Up to **8 connections** coexist; the registry holds at
most 64 identities. Equal local track IDs remain distinct by owner. A reconnect
with the same UUID/secret replaces only that connection. Do not clone an identity
configuration onto another device. Stored catalogues share a **200,000-entry
total cap**, including offline sources; excessive uploads return 413 without
replacing the old catalogue.

`STATE_DIR/bridge-credentials.json` contains SHA-256 hashes of randomly generated
256-bit credentials, UUIDs, names and revocation flags. The server reloads changes.
Rotation/revocation invalidates that owner's frames/transfers and closes its
connection (within 5 s for CLI changes; immediately through the host UI).

Legacy `BRIDGE_SECRET` is a transition for **one UUID**, pinned by the first valid
HELLO. It cannot register several devices. Keep an existing Bridge's UUID when
rotating. Its rotation/revocation permanently disables the initial secret in the
registry; stale environment variables cannot reactivate it. This transition
assumes the initial secret and first device are trusted.

From the checkout, with the server configuration loaded:

```sh
uv run openblindysir-server bridge-credential --bridge-id 12345678-1234-1234-1234-123456789abd --name 'Living room PC' --output .local/private/issued-living-room.toml
uv run openblindysir-bridge configure --credentials .local/private/issued-living-room.toml --config .local/private/living-room-config.toml
uv run openblindysir-bridge run --credentials .local/private/issued-living-room.toml --config .local/private/living-room-config.toml
uv run openblindysir-server bridge-revoke --bridge-id 12345678-1234-1234-1234-123456789abd
```

The UUID above is synthetic. Choose a different UUID per new device. To rotate,
use **the same UUID** with a new output file; existing files are refused. The
private TOML contains UUID/name/secret, but the command prints only the UUID.
Transfer it privately. `--credentials` or `OPENBLINDYSIR_BRIDGE_CREDENTIALS_FILE`
overrides stale CLI/environment/file names and secrets. Music roots and server
URL remain locally chosen. `configure` stores private settings. `doctor --connect`
registers and then disconnects; it can replace another process using that UUID.

Automation can set `BRIDGE_SECRETS`, a private JSON `{UUID: secret}` map of 1–64
distinct entries, and omit the bootstrap secret. The persisted registry is
authoritative: old environment entries do not undo rotations/revocations. An OS
lock in `bridge-credentials.lock` coordinates CLI and host changes: a competing
operation fails without overwriting the other and must be retried. The lock is
released even after process termination; do not delete its file while running.
Failed writes invalidate cached authentication and remove unusable secret output.
Issuance requires a local filesystem supporting file locks and hard links (such
as NTFS, ext4 or APFS). Managed snapshot/registry names are refused as `--output`.
The server still uses one process.

Join requests, including successful joins, are limited to 60/IP/minute and
600/server/minute. Session state retains at most 1,000 identities, including
removed players needed for current results. The usual simultaneous-player cap
remains `MAX_PLAYERS`. The identity cap rejects joins with `game_full`. **New game**
discards removed identities after archiving without changing archives; **End
session** clears every identity.

## Docker and another music device

Launchers keep volumes on `stop` and support:

```powershell
.\tools\docker-host.ps1 bridge-credential -BridgeId 12345678-1234-1234-1234-123456789abd -BridgeName "Living room PC" -CredentialOutput /data/state/issued-living-room.toml
.\tools\docker-host.ps1 bridge-revoke -BridgeId 12345678-1234-1234-1234-123456789abd
```

```sh
sh tools/docker-host.sh bridge-credential --bridge-id 12345678-1234-1234-1234-123456789abd --name 'Living room PC' --output /data/state/issued-living-room.toml
sh tools/docker-host.sh bridge-revoke --bridge-id 12345678-1234-1234-1234-123456789abd
```

The file stays private in the server volume. First create a private host
directory (`umask 077` / Windows ACL restricted to your account), then use
`docker compose --env-file .local/docker/hosting.env cp
app:/data/state/issued-living-room.toml PRIVATE_PATH/issued.toml`.
Keep the file out of Git, logs and images. Delete the server's issuance copy after
private transfer/verification; volume backups can still contain that copy.

On the other device, set `BRIDGE_SERVER` (HTTPS base URL without a path),
`BRIDGE_CREDENTIALS_FILE` (absolute private path) and `MUSIC_DIR` in a private
environment file, then:

```sh
docker compose -p bridge-living-room --env-file .local/bridge-living-room.env -f deploy/compose.bridge-credential.yaml up -d --build
```

For LAN/VPN with Caddy's private CA, set `BRIDGE_CA_FILE` to this host's public root
certificate and add `-f deploy/compose.bridge.private.yaml` after the credential
profile. It mounts the CA read-only and sets `SSL_CERT_FILE`; keep TLS verification
enabled. Public URLs with an ordinarily trusted certificate need no such override.

Music and credentials are mounted read-only; missing host paths are refused.
UID/GID 10001 must be able to read the file: on Linux use `sudo install -m 600
-o 10001 -g 10001 issued.toml PRIVATE_PATH/issued.toml` and grant only that UID
access to its parent directory. Check music-root read permissions too. Use
separate Compose project names and identity volumes. The old
`compose.bridge.yaml` remains available for the initial legacy Bridge.

## Source availability

**Bridges and connections** shows each name, UUID, software/protocol, formats,
catalogue size, jobs and scan errors. The library selects multiple owners and
folders. Offline folders retain their total count with zero available tracks.
New random choices use online owners only. A requested random choice waits
**45 seconds**, then tries another selected online source. Without one, the
round shows an exhausted pool; the host can skip, finish or reconnect. A failed
MC choice requires explicit replacement/skipping.

Prepared RAM clips and an open round continue after a disconnect; restart loses
audio. Catalogue changes affect unprepared selections; prepared/played rounds
retain captured origin/review data. New owners do not interrupt other Bridges;
the host selects their folders. Preparation, uploads and review remain bound to
the exact owner/connection/job/token. Players and a playing host during IN_GAME
receive no source names, folders or future tracks. Playing-host operational
diagnostics omit source names too.

## History and privacy

Final validation creates an independent **format-2** archive: game ID, start/end,
names/teams at validation, settings, played source names, revealed titles/artists,
locked/captured answers, ordering, server timing, scores/corrections and round
inclusion/interruption. CSV/JSON exports derive from it. No audio, audio URLs,
cookies, credentials or transfer tokens enter the archive. Later name/catalogue/
metadata changes do not rewrite completed results.

**Game history** loads on demand through host-only HTTP. During IN_GAME only the
MC can consult past games. Players see published current results. Private API
responses are not cached. Individual deletion/purge require confirmation and
exact Origin; both `session.json` and `session.previous.json` are rewritten
without the archive. A disk error rolls back the in-memory record for retry.

Simultaneous limits: **50 games, 90 days, 16 MiB** archive JSON; oldest records
are removed. Expiry runs on restore/validation and every 5 s in the server sweep.
**New game** frees the old journal/assets. Durability requires persistent
`STATE_DIR`; save errors appear to the host. Each snapshot is capped at 64 MiB:
two copies and temporarily two replacement files, worst case 256 MiB excluding
credentials and external backups. Failed/oversized saves are never reported as
successes.

Deleting an archive does not remove the **current game's** published results,
downloaded exports or external backups. **New game** replaces current results;
**End session** removes active players/answers while keeping archives/library.
Private catalogue metadata remains until replacement or operator removal of
saved state. Operators control backup retention. No accounts/cloud are added.

## Compatibility, backup and rollback

Software **0.5.0.dev0**, network **10** (accepted **10..10**), snapshot **8**, history
**2** have different roles. Update server, Bridge and web build together. Public
`/api/compatibility` exposes only compatibility numbers. An incompatible web
client shows the range/update action without endless reloads. The Bridge exits
with code 4 and a required range. No automatic downgrade.

Snapshots **1/2/3/4/5/6/7/8** are readable; unversioned/format-1 history migrates to 2.
Missing old settings/start dates/source names remain absent. Old cookies migrate
when passwords and the old deployment secret match. Format-4 cookies depend only
on game/host passwords; Bridge rotation preserves players. Unknown future
snapshot/history versions stop recovery even with an older backup, avoiding
silent rollback of published scores. A corrupt primary tries a validated backup;
two invalid copies stop startup rather than inventing an empty game.

Before upgrading, stop services and privately copy `STATE_DIR`, server/Bridge
configs and credentials; retain the matching installation. Roll back the **whole
installation plus pre-migration backup**. V0.3 cannot read format 4, and new
answers do not merge backwards. Verify host access, versions, saving, each
reconnected UUID and archived results after restoring.

An interrupted OPEN round captures received drafts and returns to marked review;
it never automatically replays. Unstarted rounds return to preparation. Published
scores stay frozen. Host diagnostics show versions, job owners, connections,
save status and history size. Anonymize private nicknames/source names before
sharing. Bridge `doctor --json` excludes identifiers/paths/addresses/secrets.

The protocol remains **evolving**. Future breaking changes increment its number,
ship migrations/guides and announce accepted range/deprecation. Deprecated
commands are explicitly refused. V0.5 promises neither freeze nor long-term
compatibility.

## Accessibility and verification

Game/host skip links, phase focus without stealing typing, text announcements,
accessible names/states, keyboard confirmations with Escape/focus restoration
and audio-position minutes/seconds are implemented. Tests cover text colours,
44 px targets, 320/390/1280 px layouts, 200% text enlargement and reduced motion.
320 px layout checks reflow corresponding to 1280 px at 400% zoom; no screen
reader is simulated.

NVDA/JAWS/VoiceOver, real Safari/iOS/Android, acoustic timing, large personal
libraries and all native runners remain manual checks. Chromium/WebKit tests
are not WCAG certification. See [testing](testing.md), [UX](UX.md),
[security](../SECURITY.md) and [ADR 0015](adr/0015-v05-private-bridges-history-compatibility.md).
